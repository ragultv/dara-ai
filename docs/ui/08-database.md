# Local database

All app data (chat history, settings, per-model configuration) lives in one SQLite database, so it survives restarts and updates, can be exported and deleted in one place, and never depends on the WebView's storage (which can be cleared). Schema: [db/schema.sql](db/schema.sql) (tested: tables, cascades, full-text search).

## Where it lives

`%LOCALAPPDATA%\Dara\dara.db`: the same per-user Dara data folder as the models and `calibration.json`. Not the install folder: Windows installs go under `Program Files`, which a normal user cannot write to, and an update or uninstall would delete the data. Images go to `%LOCALAPPDATA%\Dara\attachments\` as files; the database stores only their names. The folder follows the user's profile and its default Windows permissions (readable by that user only).

Settings can move the *models* folder; the database and attachments stay in the Dara data folder.

## Who owns it

The **Rust side of the Tauri app** owns the database (crate `rusqlite` with the `bundled` feature, so no system SQLite is needed). The WebView never gets raw SQL access and the SQL plugin is not installed: the UI calls a small set of typed Tauri commands and the Rust side runs fixed, parameterized statements. This keeps a compromised WebView from reading or rewriting arbitrary data (see 05), and keeps SQL out of the React code.

The server (`dara.exe`) does not touch this database; the API stays stateless.

Connection setup (every open): `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA foreign_keys=ON; PRAGMA busy_timeout=5000;`. One writer connection behind a mutex plus a read connection is enough. Memory: keep SQLite's page cache small (`PRAGMA cache_size=-2000`, about 2 MB) so the database adds almost nothing to the 300 MB budget.

## Tables (summary)

| Table | Holds |
| --- | --- |
| `settings` | key/value JSON: theme, port, models folder, LAN toggle, defaults for K/V format, Flash, VRAM reserve, vision, sampling, system prompt, tray and autostart |
| `conversations` | id, title, model, system prompt, per-conversation parameters, pinned, timestamps |
| `messages` | conversation, position, role, content (text/Markdown), finish reason, error, stats JSON (usage, timings, context, speculative), model, time |
| `attachments` | image files of a message: mime, file name, thumbnail, size |
| `model_configs` | what the user chose per model (K/V format, Flash, vision, context); no row means Auto |
| `messages_fts` | full-text search index over message content (kept in sync by triggers) |

What is **not** stored: the API key (memory only, regenerated each run), model files and calibration measurements (the server owns them), message HTML (only the raw text; Markdown is rendered and sanitized at display time).

## Tauri commands (the UI's only way in)

Defined in `src-tauri/src/db.rs`, registered with `invoke_handler`, each with a typed request and response (types mirrored in `app/src/lib/db/types.ts`):

`settings_get_all`, `settings_set(key, value)`, `conversations_list(limit, cursor)`, `conversation_create`, `conversation_update(id, patch)`, `conversation_delete(id)`, `messages_load(conversation_id)`, `message_append(...)`, `message_update(id, content, finish_reason, stats)` (used when a streamed reply finishes; write the reply once at the end plus a throttled checkpoint every few seconds so a crash loses little), `attachment_add(message_id, bytes, mime)`, `search(query, limit)`, `model_config_get/set`, `data_export` (JSON file via a save dialog), `data_delete_all`, `db_info` (size, schema version).

Validation in Rust: ids are UUIDs, roles and enums match the CHECK constraints, content length capped (e.g. 2 MB per message), attachment mime sniffed from the bytes, file names generated by the app (never taken from the user), paths never accepted from the WebView.

## Migrations

`PRAGMA user_version` holds the schema version. On start: if the file is newer than the app knows, open read-only and tell the user to update; if older, copy `dara.db` to `dara.db.bak-v<N>` first, then run the forward-only migration files in order inside one transaction, then bump the version. Never edit an applied migration; add a new file `db/000N_name.sql`. Each migration has a test that upgrades a database filled with sample data.

## Reliability

- WAL mode; the database is checkpointed on exit. If it fails the integrity check on start (`PRAGMA quick_check`), keep the damaged file as `dara.db.corrupt-<time>`, start a fresh database, and show a message with the backup's location.
- All writes are small transactions; a streamed reply is appended in memory and written at the end and at checkpoints.
- Disk full or read-only: show the error, keep the conversation in memory, keep generating, retry on the next write.

## Privacy and deletion

- Local only; never uploaded. No analytics rows.
- "Delete all data" removes the rows, runs `VACUUM`, and deletes the `attachments` files, after a confirmation that names what will be lost. Deleting one conversation deletes its messages (cascade), its attachment rows and files, and its search entries.
- Encryption at rest is not on by default (the data is protected by the user's Windows profile). If users ask for it, SQLCipher or Windows DPAPI-wrapped keys are the options; do not invent a home-made scheme.
- Diagnostics and logs never include message content.

## Tests

Rust unit tests on a temporary database: create/append/load, cascade delete, FTS search and its sync triggers, constraint rejections (bad role, bad kv), migration from each past version, `data_delete_all`, corrupt-file recovery. A UI-side fake of the commands (in `app/mocks`) lets React tests run without Tauri.
